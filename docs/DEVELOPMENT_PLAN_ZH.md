## 1. 产品目标与边界

PromptForge 的目标不是一个简单的提示词收藏夹，也不是把一段长文本拼接起来的工具，而是一个**可追溯、可验证、可移植、可扩展的提示词工程平台**。

核心产品结构：

```text
提示词资产库
    │
    ├── 项目 / 任务上下文
    │
    ▼
统一 Prompt Kernel
    ├── 资产解析与依赖展开
    ├── 角色与顺序约束
    ├── 变量合并与模板渲染
    ├── 冲突、安全与预算校验
    ├── 确定性编译
    └── Compile Manifest / 历史快照
    │
    ▼
统一 Adapter Contract
    ├── Cursor Rules
    ├── Claude Code
    ├── ChatGPT
    ├── 通用 API / OpenAI-compatible
    └── 本地 AI 工具
```

### 1.1 必须坚持的设计原则

1. **一个统一内核：** 不为 Cursor、Claude Code、ChatGPT 分别复制一套提示词拼接逻辑。
2. **适配器只负责目标转换：** 资产解析、依赖关系、变量和编译规则由 Kernel 统一处理。
3. **编译结果可复现：** 相同资产快照和编译参数必须得到相同的消息、文本、诊断顺序和 Manifest。
4. **资产修改可追溯：** 每次编译保留精确资产快照，后续编辑不能改变旧编译记录。
5. **默认本地优先：** 提示词和项目数据默认保存在本地；未经用户明确操作，不发送到外部模型。
6. **外部写入必须可控：** 初期只生成下载文件，不静默覆盖用户项目文件。未来如增加同步，必须先展示差异、备份并允许回滚。
7. **证据驱动：** 设计、实现、单元测试、集成测试、真实平台验证和实物/生产验证必须分开标记。
8. **不提前扩张范围：** 不在核心工作流稳定前启动云协作、市场、向量数据库或自主 Agent。

### 1.2 核心用户工作流

最终必须完整支持：

1. 创建、导入或复用提示词资产。
2. 维护资产角色、分类、标签、变量、依赖、冲突和版本。
3. 按项目与任务组织上下文。
4. 显式选择根资产，查看自动展开的依赖树。
5. 填写变量并检查缺失值、冲突和预算。
6. 预览分角色消息、最终文本和目标平台文件。
7. 编译并保存可复现的 Manifest。
8. 导出到指定 AI 工作流。
9. 查看历史、比较版本、重新生成旧结果。
10. 备份、迁移和恢复全部提示词资产。

4. API 请求体、单资产内容、依赖数量、变量数量和总编译输出的统一资源上限尚需系统审计。
5. Cursor / Claude Code 等适配器仍需真实目标项目兼容性验证；当前不等于 IDE 插件或自动写入。
6. TokenCounter 的真实模型 tokenizer 覆盖尚未完成。
7. 提示词资产完整导入/导出、数据库备份恢复尚未完成。
8. API 无认证；代码强制 loopback 监听，不能暴露到公网或不可信网络。
9. 仓库尚未提交 `package-lock.json`，依赖版本还不能完全锁定，需生成 lockfile 并切换 CI 到 `npm ci`。

## P2：生产可靠性、资源限制与安全

这是进入长期使用前的强制阶段，不允许仅凭单元测试通过就跳过。

### REL-01：SQLite 并发和崩溃恢复

- 审计当前 journal mode、busy timeout、事务边界和连接生命周期。
- 多个 Node.js 进程同时读写同一个 SQLite 文件。
- 覆盖同时创建资产、保存版本、编译、写历史、读取历史。
- 检查 SQLITE_BUSY、锁等待、事务回滚和进程异常退出。
- 根据实测决定是否采用 WAL、连接协调或单实例锁；不预设未经验证的方案。
- 验证迁移期间崩溃不会留下半迁移状态。

验收：无静默丢失、无重复版本、无半条编译历史；失败必须可诊断、可恢复。

### REL-02：输入和资源预算

为以下输入建立明确、可配置的限制：

- HTTP 请求体最大字节数。
- 单个资产内容长度。
- 单次编译选择资产数量。
- 依赖节点数和依赖边数。
- 变量总数、变量名称长度和值长度。
- 单次编译输出字节数。
- Token 预算上限。
- 单次导入资产数量和总文件大小。

超限时返回稳定的结构化诊断，不允许进程崩溃或无限占用内存。

### REL-03：真实网络压力与长时间测试

测试工具可选 k6、autocannon 或 wrk；先建立可复现脚本，再确定容量目标。

测试矩阵：

| 负载 | 目的 |
|---|---|
| 10 / 50 / 100 并发 | 基础吞吐和延迟 |
| 200 / 500 并发 | 并发退化和排队 |
| 1,000 并发 | 找到系统拐点，不预设必须通过 |
| 30 分钟 Soak | 首轮长时间稳定性 |
| 60 分钟 Soak | 发布候选版本验收 |

必须记录：
- 请求吞吐量和成功率。
- p50 / p95 / p99 延迟。
- 4xx / 5xx / 超时 / SQLite 锁错误。
- RSS 峰值、heap 使用、GC pause。
- CPU 使用和事件循环延迟。
- 编译记录数量与持久化完整性。

容量阈值在首轮真实网络基准测试后确定，不能用单次 `app.inject` 时间冒充生产 SLA。

### REL-04：本地 API 安全

- 默认仍只监听 `127.0.0.1`。
- CORS / Origin 校验和请求体限制纳入测试。
- 非 loopback 监听必须要求明确配置，并在启用前强制提供认证机制。
- 不在普通日志中输出完整提示词、用户私密变量或密钥。
- 任何未来的模型 API 密钥不得以明文保存在普通资产表中。
- 资产内容和变量值只作为文本处理，不执行模板注入后的代码或二次模板。

### REL-05：备份恢复

- 支持创建一致性数据库备份。
- 支持恢复到独立路径并先校验，再替换当前数据。
- 覆盖备份期间仍有编译请求的情况。
- 记录备份时间、数据库 schema 版本和校验结果。
- 恢复失败不能破坏原数据库。

### P2 验收

- 多进程并发写测试通过。
- 真实网络压测有完整原始结果和脚本。
- 30 分钟 Soak 无数据丢失、无不可恢复错误；60 分钟作为发布候选门槛。
- RSS、GC 和 CPU 数据可复查。
- API 超限和安全边界测试通过。
- 备份恢复往返测试通过。

## P3：资产库与组合工作台体验

原则：补齐真实工作流，不为了界面复杂而堆叠面板。

### UX-01：资产库

- 角色、分类、标签、项目、更新时间和使用频率筛选。
- 关键字搜索支持名称、说明和内容。
- 资产详情显示版本历史、依赖和冲突。
- 支持批量标签和批量导出；批量删除必须二次确认。
- 清楚区分资产当前版本与历史快照。

### UX-02：可视化依赖编辑

- 用树或图展示依赖展开关系。
- 标记显式选中根节点与自动展开依赖。
- 在添加依赖前检查环和不存在的引用。
- 冲突时展示具体冲突资产和声明方向。
- 不允许 UI 的视觉顺序覆盖 Kernel 的权威解析顺序。

### UX-03：变量工作台

- 自动收集已选资产的变量 schema。
- 展示 required、default、描述和输入值。
- 同名变量定义冲突时明确显示来源资产。
- 提供空值、缺失值、未声明值和特殊字符的即时诊断。
- 变量值不得被二次解析为模板表达式。

### UX-04：编译与历史

- 编译前显示资产数量、依赖数量、角色数量和 Token 估算。
- 编译后展示角色消息、纯文本和目标适配器产物。
- 历史记录支持查看、复制、比较和重新导出。
- 历史记录的 Manifest 必须可追溯，不允许读取资产当前内容替代旧快照。

### 验收

- 新用户可以独立完成创建资产 → 组合依赖 → 填写变量 → 编译 → 导出 → 查看历史。
- 关键诊断有明确定位和修复路径。
- 主要页面在常见桌面尺寸下无横向溢出和信息堆叠。
- 浏览器测试覆盖主流程和至少一个失败修复流程。

## P4：资产导入、导出与数据可移植性

### DATA-01：规范化 JSON Bundle

设计带 schema version 的标准包格式，至少包含：

- 包格式版本。
- 资产 ID、名称、角色、内容和元数据。
- 分类、标签、优先级。
- 变量 schema。
- 依赖与冲突关系。
- 资产版本快照。
- 可选的项目和任务上下文。
- 导出时间与 PromptForge 版本。

禁止导出 API 密钥、操作系统凭据和其他秘密。

### DATA-02：安全导入

导入必须先执行 Dry Run：

1. 解析包格式和版本。
2. 校验字段类型、长度和枚举。
3. 检查重复 ID、缺失依赖、循环和冲突。
4. 显示将新增、更新、跳过和重命名的资产。
5. 用户选择冲突处理策略。
6. 在事务中执行导入。
7. 失败时整体回滚。

### DATA-03：往返与兼容性

- 导出 → 清空测试库 → 导入 → 再导出，规范化内容一致。
- 不支持的 schema 版本必须拒绝或走显式迁移。
- 老版本包迁移必须保留原始 ID 和可追溯版本。
- 导入失败不产生半成品资产。
- 提供数据库备份作为完整数据恢复的兜底。

### DATA-04：文件导入方向

先完成 JSON Bundle，再按优先级支持：
- Markdown / TXT 提示词。
- Cursor Rules 文件。
- Claude Code 指令文件。

导入外部文件时，必须保留原始文件名、来源路径和导入时间；无法可靠解析的内容作为普通文本导入，不猜测其结构。

## P5：平台适配器与外部工作流

### ADP-01：统一 Adapter Contract

所有适配器必须实现同一接口：

```text
AdapterId + successful CompileResult + target metadata
    -> AdapterArtifact
```

统一产物字段：
- 文件名或建议路径。
- MIME 类型。
- 文件内容。
- 目标平台和格式版本。
- 安装/放置说明。
- 来源资产与 Manifest 关联信息。

适配器不得重新实现依赖解析、变量合并或冲突判断。

### ADP-02：逐个平台验证

| 目标 | 计划工作 | 验收证据 |
|---|---|---|
| Cursor | 核实当前 Rules 格式、文件位置、规则元数据和作用范围 | 真实 Cursor 项目加载结果 + fixture |
| Claude Code | 核实 CLAUDE.md 与规则目录的组织和加载行为 | 真实 Claude Code 项目结果 + fixture |
| ChatGPT | 提供适合复制粘贴/导入的角色化提示词包；不宣称有未实现的直连能力 | 导出内容检查 + 实际使用记录 |
| 通用 API | 输出保留 system/developer/user 的结构化 JSON | JSON Schema/契约测试 + 示例请求验证 |
| 本地 AI | 提供纯文本和结构化消息输出；再按实际本地工具补充适配 | 目标工具加载或请求记录 |

目标平台格式会变化。实现前必须查验对应版本的官方文档，并记录验证日期和软件版本。

### ADP-03：真实集成边界

第一阶段仍以可下载文件和用户确认后的复制为主。

后续如增加自动同步或 IDE 插件，必须独立立项并提供：
- 写入前 Diff 预览。
- 目标路径白名单。
- 文件备份。
- 用户明确确认。
- 原子写入。
- 一键回滚。
- 外部项目不存在或格式不支持时的安全失败。

### ADP-04：真实 TokenCounter

- 为目标模型提供可替换的 TokenCounter。
- tokenizer 版本与模型 ID 必须记录。
- 对中文、英文、代码、混合文本和特殊字符建立测试集。
- 对比 heuristic-v2 与真实 tokenizer 的误差分布。
- 没有对应 tokenizer 时继续明确标注 approximate，不伪造精确值。

## 6. 并行研发安排

允许并行，但必须隔离文件和职责，避免多个窗口修改同一个核心文件。

| 工作流 | 负责范围 | 允许并行的前提 |
|---|---|---|
| A：主线集成 | PR 审查、分支基线、看板 | 不与专项同时修改同一分支 |
| B：Kernel/UI | 角色编辑、结构化预览、Manifest | 以已确认的 Kernel API 为接口 |
| C：可靠性 | SQLite、API 限额、多进程测试 | 独立测试分支，不擅自改 Kernel |
| D：数据迁移 | JSON Bundle、备份恢复 | 先固定数据 schema 契约 |
| E：Adapter | Cursor / Claude Code / ChatGPT / Local | 只实现适配器和 fixture，不改 Kernel |
| F：发布工程 | 安装包选型、运行环境测试 | 等待 API/数据目录契约稳定 |

### 并行研发约束

1. 每个专项声明共同基线 SHA。
2. 先读现有实现，不重复开发已完成内容。
3. 每个专项使用独立分支和 PR。
4. 不直接推送 main。
5. 不将不同 SHA 的测试结果拼接成同一个通过结论。
6. 共享接口变更必须先提交设计或 Issue，再由总控协调。
7. 完成后交付代码、测试命令、日志、提交 SHA 和已知限制。

## 7. 质量门槛与完成定义

任何功能必须分别记录以下状态，不得混用：

1. **已设计**：需求、边界和验收标准已确定。
2. **已实现**：代码已经提交。
3. **单元测试通过**：局部逻辑通过自动化测试。
4. **集成测试通过**：模块间数据流和持久化通过。
5. **端到端通过**：真实用户流程在浏览器或应用中跑通。
6. **目标环境验证通过**：目标平台、真实网络或真实部署环境已验证。
7. **发布验收通过**：升级、备份、安全、性能和回滚满足发布门槛。

每个完成项必须能追溯到：
- Issue / PR。
- 完整 commit SHA。
- 测试命令和运行环境。
- CI Run 或原始日志。
- 测试输入和关键输出。
- 失败记录与未覆盖范围。

项目看板只展示最高级别的真实证据。计划完成、代码存在或 CI 的局部通过都不能直接标记为发布完成。

## 8. 明确暂缓的方向

在 P0–P5 的核心闭环完成前，不启动以下方向的产品级研发：

- 云同步、账号系统和多人实时协作。
- 提示词市场、公开分享和社区评分。
- 向量数据库、Embedding 和自动语义检索。
- 由 LLM 自主决定资产选择或自动改写用户提示词。
- 模型训练和微调。
- 无用户确认的外部项目文件自动覆盖。
- 多租户 SaaS 和公网 API 服务。

这些方向可以保留技术调研，但不能挤占核心产品的可靠性、数据可移植性和平台兼容性工作。
